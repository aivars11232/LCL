LEARNED COMPUTING LANGUAGE (LCL)
TITLE: Verify, Test, Evidence, Success, Failure, and Status
LANGUAGE VERSION: 0.1.0
STATUS: NORMATIVE
DATE: 2026-09-05


VALIDATE observes preconditions. VERIFY observes postconditions. TEST compares
EXPECTED/ACTUAL or ASSERT. Required failed checks prevent success. EVIDENCE must
be observable, typed, and traceable; declared required provenance/checksum must
resolve.

SUCCESS evaluates ALL, ANY, or NONE after execution/checks. At a TASK execution
root, status.succeeded is legal only when its SUCCESS is TRUE, all required outputs
are fully bound and valid, all hard rules hold, and all required evidence
exists. status.partial is explicitly non-success. FAILURE blocks may map exact
WHEN conditions to terminal non-success statuses. Resolve status and error
aliases to their canonical core identifiers before evaluating these contracts;
an alias inherits the exact terminal and non-success restrictions of its BASE.

An existing primary unhandled diagnostic always fixes status by its resolved
default_status, including any exact expression-demand override. A FAILURE
mapping cannot override that diagnostic. Otherwise
evaluate applicable FAILURE clauses in source declaration order and select the
first whose WHEN is TRUE. FALSE does not select a clause. MISSING or UNKNOWN is
a required-condition failure using error.required.missing or error.value.unknown
and follows ordinary diagnostic handling before a later clause is considered.
The selected clause requests its terminal non-success STATUS, which must occur
in the current invocation state's allowed_next. An illegal requested transition
uses error.execution.order. Its optional ERROR
is a classification of that declared failure, not emission of a new diagnostic
at an arbitrary stage, and therefore raises no event by itself. Its required
EVIDENCE must still resolve. A selected declared failure prevents success even
when other SUCCESS conditions are TRUE. If no primary diagnostic or declared
failure fixes a non-success outcome and SUCCESS is unsatisfied, use
error.success.unsatisfied. No additional generic success diagnostic replaces an
already selected declared failure. A root FAILURE mapping cannot select
status.skipped, even through an alias; that status has non-root scope and the
illegal request uses error.execution.order.

status.blocked is terminal for one invocation; a later explicit invocation has
its own lifecycle and retains the earlier result as evidence. Only non-root
declarations may move from status.ready to status.skipped when applicability is
FALSE or they are optional and omitted. Neither blocked nor skipped denotes
successful completion of required work.

A result record's status is instead scoped to the producer invocation. Producer
status.succeeded means that invocation completed its contract; its domain
outcome remains independent. A completed TEST may record passed FALSE, a
completed VALIDATE may record valid FALSE, a completed VERIFY may record
verified FALSE or UNKNOWN, and completed dispatch may record delivered FALSE or
UNKNOWN without turning producer completion into execution failure. The
execution root still fails whenever its own required SUCCESS, OUTPUT, rule, or
evidence condition is unsatisfied.

UNKNOWN in passed, verified, delivered, changed, or transfer bytes is a transient
observation only. It never binds OUTPUT and therefore cannot satisfy a required
output or required Boolean success condition. A material FALSE remains a valid
bound result value when the declared OUTPUT type permits BOOLEAN; its truth is
then evaluated normally by any separate SUCCESS condition.

CHECK SELECTION AND ROOT COMPLETION

Authority: 10_REGISTRIES/statuses_and_errors_v0.1.0.json#/check_selection_contract

SELECTION
Select VALIDATE, VERIFY, and FAILURE declarations in the EXECUTE root source
document. A targetless clause applies to that invocation. For pre-effect
VALIDATE, a resolved TARGET must name a candidate graph member, a data/output
declaration explicitly referenced by that graph, or the exact material/address
TARGET selected by a graph ACTION. Match declaration identity or material
identity under types_v0.1.0.json#/material_identity_contract; never expand
ambient resources. Targeted post-execution VERIFY applies only to an actually
activated producer or an observed target of that invocation, not an unselected
IF branch merely present in the candidate graph. Include check prerequisites
explicitly referenced by selected checks or the root SUCCESS. Unrelated
imported checks never run merely because their document was imported. TEST
declarations are activated only as an explicit TEST root or operation target,
never as ambient tasks.

PREREQUISITES
Evaluate selected check-result prerequisites in stable topological order with
source-unit namespace then source declaration order as tie-breakers. A
prerequisite cycle uses error.reference.cycle. Check references observe one
scheduled result rather than rerunning the check. Every selected pre-effect
VALIDATE, including an optional check or prerequisite, must be evaluable before
effects and cannot depend on future OUTPUT or a post-execution check.

DEMAND
Every selected and applicable VALIDATE is evaluated before any effect. REQUIRED
controls whether a FALSE result blocks, not whether a selected check runs.
VERIFY follows its actually activated producers or observed targets. A TEST
root executes only its explicit TASK or ACTION, if present, then evaluates
ASSERT or EXPECTED/ACTUAL. Where WHEN exists, absence means TRUE and FALSE
skips applicability. A skipped check has no result; an explicit required read
of that absent result uses ordinary MISSING behavior, never implicit TRUE.
Required demanded MISSING and UNKNOWN use error.required.missing and
error.value.unknown. No WHEN field is invented for TEST.

FAILURE
A required FALSE VALIDATE assertion uses error.validation.failed. A required
post-execution FALSE VERIFY or TEST assertion uses error.verification.failed.
Optional FALSE checks retain their Boolean domain outcome without emitting a
required-check failure. An ERROR field is exact classification metadata; it
does not emit a diagnostic with an unrelated stage or override the
required-check diagnostic.

DOMAIN RESULTS
A core.test invocation can complete result production with passed FALSE. Its
producer status and domain result remain independent. Any separate required
TEST obligation belongs to the enclosing root or check invocation, not to
fabrication of the result record.

ROOT SUCCESS
A TASK root evaluates its referenced SUCCESS. A TEST root evaluates ASSERT, or
strict EXPECTED/ACTUAL equality when ASSERT is absent; if both are present they
must both hold. PHASE, SEQUENCE and ACTION roots succeed when all applicable
required graph, check, rule, evidence and OUTPUT obligations complete, without
requiring an unavailable SUCCESS field. FALSE root completion uses
error.success.unsatisfied unless a primary diagnostic or selected FAILURE
already fixes the outcome.

LIFECYCLE
A root enters status.running before evaluating dynamic execution/control or
post-execution completion even when its graph has no executed ACTION.
Registered execution-stage diagnostics discovered before effects may take
status.validating or status.ready to status.failed; this never changes their
producer-relative failure_phase or creates effects.
