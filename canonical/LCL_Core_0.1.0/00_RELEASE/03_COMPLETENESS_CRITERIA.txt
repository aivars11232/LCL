LCL CORE 0.1.0
RELEASE COMPLETENESS CRITERIA
NORMATIVE

This version is BARE_SPECIFICATION_COMPLETE when the actual language-definition
bytes provide and freshly validate all of the following, independently of final
packaging:

- a closed character, token, keyword, symbol, identifier, and literal system;
- a closed grammar with no external token-list placeholders;
- a closed type system and special-value model;
- exact legal parents, occurrence, field type, cardinality, default, and
  conditional requirements for every core block;
- deterministic expression, operator, order, conflict, error, and status rules,
  including closed stage selection, specificity, supersession, duplicate,
  location, stable-order, primary, secondary, and recovery behavior;
- exact target, named-parameter, determinism, dependency, effect,
  invocation-resolution, applicable-error, and result-schema-reference contracts
  for every core operation, plus exact contracts for every pure function;
- nine closed result schemas with exact common and schema-specific fields,
  cardinality, domain-outcome, execution-status, failure-phase, effect-state,
  partial-effect, and OUTPUT projection/binding contracts;
- producer-relative failure lifecycle rules for every registered error, including
  allowed phases, status selection, effect truth, OUTPUT binding, retained
  evidence, indeterminate state, and bounded retry safety;
- closed import, namespace, reference, version, and extension behavior;
- required conformance cases covering every closed registry entry;
- valid and deliberately invalid examples with registered expected diagnostics.

The current candidate must freshly establish every criterion above; historical
task acceptance does not establish current completeness. BARE_SPECIFICATION_COMPLETE
does not by itself mean packaged or release-ready. Release completeness additionally requires:

- a documented cryptographic integrity model covering every distributed payload,
  with any unavoidable manifest/checksum self-exclusions stated explicitly;
- a validation report bound to the exact manifest and, only for a release-ready
  package, the exact archive that it validates.

Candidate integrity is acyclic. Stable payload files exclude MANIFEST.json,
VALIDATION_REPORT.txt, and SHA256SUMS.txt. MANIFEST.json lists and hashes every
stable payload file and excludes itself and the two later-generated files.
VALIDATION_REPORT.txt records the manifest hash and the Gate 1 through Gate 8
snapshot. SHA256SUMS.txt then hashes every package file except itself, including
the manifest and validation report. External validation reports, outside the
package root, record the final hashes and Gate 9 result. An archive is permitted
only after Gates 1 through 9 all pass with no release blocker.

A gate whose only evidence would be a lexer, parser, interpreter, compiler,
runtime, or semantic execution engine is outside this package's scope. Such a
gate is reported as OUT_OF_SCOPE, is never reported as PASS, and never blocks
release. LCL-TASK-0007 classified an earlier snapshot BARE_LANGUAGE_RELEASE;
that historical classification does not apply to this modified candidate.

A candidate with an unresolved language contradiction, undefined contract, invalid
positive example, or unexpected applicable conformance result is not
BARE_SPECIFICATION_COMPLETE. A stale validation report, manifest mismatch, or
archive-integrity failure means the candidate is not Final, Verified,
packaged-release-complete, or release-ready; that packaging state does not by
itself reverse a separately and freshly evidenced BARE_SPECIFICATION_COMPLETE
classification.

Empirical agreement by ChatGPT, Claude, DeepSeek, or another LC is a conformance
experiment. It is not part of defining the language.
